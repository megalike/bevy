# MPS patches on Bevy

This fork carries the changes Motion Pipes Studio (MPS, <https://github.com/megalike/MotionPipesStudio>) needs on top
of a Bevy release. Everything else is Bevy as released. MPS's rules for this fork: `knowledge/BEVY-FORK.md` in MPS.

## Conventions

- One branch per Bevy release: `mps/0.20.1` starts at the tag `v0.20.1`. A Bevy update starts `mps/0.21` at `v0.21.0`
  and carries over every patch below that the new release does not already contain (merged on Bevy's `main` is not
  enough).
- One change per pull request into `mps/<version>`, from a topic branch (`fix/…`, `feat/…`, `improve/…`, `perf/…`),
  squash-merged to one commit whose subject says what it is: `fix(<crate>):` a Bevy bug, `feat(<crate>):` something
  Bevy lacks, `improve(<crate>):` better quality or API, `perf(<crate>):` speed; `docs(mps):` for this file. Labels on
  the pull request say the same (`bug`, `feature`, `improvement`, `performance`) and where it may go
  (`upstream-candidate`, `mps-only`). A patch adds its row below in the same commit.
- Commit trailers, written into the squash message: `MPS-Kind` (fix / feature / improve / perf / mps-only),
  `MPS-Decision` (the MPS decision that asked for it), `MPS-Evidence` (the MPS report with the measurements). The
  upstream status (not filed / an issue or PR link / contained in a release) is kept in the table below.
- Tags mark the revisions MPS uses: `mps-<bevy version>.<n>`, for example `mps-0.20.0.1`, never moved once pushed,
  each with a GitHub release listing its patches. MPS pins exactly one tag.
- Upstream contributions are separate branches from Bevy's current `main` and follow Bevy's contribution guide and AI
  policy; the owner writes and submits them himself.

## Patches on `mps/0.20.1`

| Patch | Kind | Crate | What | Upstream |
| --- | --- | --- | --- | --- |
| Receiver-plane depth for spot-light PCSS | fix | bevy_pbr | Every blocker-search and filter tap of spot-light PCSS compares with the receiver plane's depth at the uv it reads, not one depth for all taps: grazing-lit walls no longer show self-shadowing combs. Forward rendering only (Bevy's deferred lighting pass has the normal-mapped normal and keeps one depth); the plane comes from the interpolated vertex normal | not filed (candidate after a minimal repro and deferred and smooth-mesh coverage) |
| Contact shadows fade with hit distance | improve | bevy_pbr | Screen-space contact shadows fade by the blocker's world distance along the ray, so long hard lines that a soft light would not draw fade out while tight contacts stay dark; applies to spot, point and directional lights and also weakens true hard-light contacts half-way along the ray | not filed (to discuss upstream as an option, not a new default) |
| Soft contact shadows from the light's size | feature | bevy_pbr | For a point or spot light with soft shadows under temporal shadow filtering, each pixel and frame marches the contact-shadow ray towards one point of the light sphere's apparent disc (uniform in solid angle, a PCG stream per pixel, frame and light) and TAA averages the penumbra; lights without a size, the directional light and other filter methods keep one hard ray | not filed (candidate; needs a motion and TAA-history check) |
| Spot-light PCSS minimum filter | improve | bevy_pbr | The receiver-plane spot PCSS never filters narrower than `SPOT_PCSS_MIN_BLUR` (2.0 `blur_size` units, an outer tap radius of about 3.7 shadow-map texels, against 0.5) like EEVEE's per-light filter radius: casters a texel or two wide are soft bands instead of aliased streaks, real contacts soften by that footprint; Bevy's deferred lighting pass keeps 0.5 | not filed (depends on the receiver-plane patch; an option, not a default) |
| Lint fixes for the fork's CI | mps-only | bevy_dev_tools, bevy_solari, bevy_pbr | Two dependency lines in the release manifests take the one-line form `taplo` asks for (only formatting, not in `main`, which still has `-dev` versions); American spelling in the patches' comments; no shader or dependency change | not applicable |
| Per-view environment map settings, a capture origin, priorities and a specular-only generator for reflection probes | feature | bevy_light, bevy_pbr | `EnvironmentMapSettings` on a camera excludes every local light probe from that view (`use_local_probes: false`, for a camera that captures a reflection probe) or takes the diffuse environment term once from the view's own environment map while reflection probes supply only the specular term (`diffuse_from_view`); box projection forms the cubemap sample direction in world space from the capture point (`ReflectionCaptureOrigin`, by default the probe's origin) and rotates it into the probe's frame without the box scale, where it sampled the hit in normalized probe coordinates, which distorted directions in a box that isn't a cube and scaled direction-only sampling; box projection takes the ray's exit from the slabs (per axis the plane it travels towards, then the minimum; a parallel axis never limits, a ray leaving behind its origin stays at the fragment) where the nearest positive plane jumped between a face and the far wall for a fragment on a face; `ReflectionProbePriority` on a probe: where a higher-priority probe has weight w, lower-priority probes supply only the residual 1 - w and the view's map what remains (a room inside a hall; equal priorities blend as before); `GeneratedEnvironmentMapSpecularOnly` beside a `GeneratedEnvironmentMapLight` skips the 32x32 irradiance convolution (the diffuse map stays black); a fragment between a probe's `ParallaxCorrection::Custom` boundaries and its influence box takes the probe only if its shading normal faces into the boundaries along every axis it overshoots (the floor outside a doorway still blends, a wall's outer face, a floor's underside and a roof's top do not; `Auto` and `None` are unchanged); the probe uniform grows by a quaternion, a point and an integer | not filed (the projection fix is a bug-fix candidate; the settings, the capture origin, the priority and the specular-only marker options to discuss) |
| Forward-MRT screen-space reflections | feature | bevy_core_pipeline, bevy_pbr | `ScreenSpaceReflectionsMode::{Deferred, ForwardMrt}` on `ScreenSpaceReflections` (default `Deferred`, the stock behavior); `manage_ssr_prerequisites` inserts the mode's prerequisite (`DeferredPrepass`, or the new camera marker `ForwardSsrGBuffer`) and removes only what it inserted. With the marker (and `Msaa::Off`) the view gets `ViewSsrGBuffer` (`Rgba32Uint`, the target's size), the main opaque pass attaches it as color target 1 cleared to zero, and `MeshPipelineKey::FORWARD_SSR_MRT` adds the matching target and the shader def `FORWARD_SSR_MRT` to the `Opaque3d` / `AlphaMask3d` draws only (stripped for transmissive, transparent, prepass, shadow and wireframe pipelines): `FragmentOutput` gains `@location(1) packed: vec4<u32>` in Bevy's deferred packing with the flag bit `DEFERRED_FLAGS_FORWARD_SSR_RECEIVER_BIT`; every shader drawn into the pass writes valid receiver data or zero (`pbr.wesl` and the skybox write zero: an output left unwritten behind an empty write mask was not left alone on NVIDIA Vulkan). The forward pass (`forward_screen_space_reflections`, after the opaque pass, before transmission and transparency, so TAA, bloom and tonemapping see the reflections) decodes the G-buffer, skips invalid receivers and receivers outside the roughness window, casts Bevy's stochastic GGX ray (`raymarch.wesl` unchanged) and replaces the receiver's share of the environment specular the opaque pass added, `C + q O (W H - exposure E)`, with `E` the receiver's `environment_map_light(..., true).specular` through the view's probe bindings (selection at the receiver), `O` Lagarde's specular occlusion from the view's GTAO times the packed occlusion (the material's authored shade), `q` the hit's border confidence times the roughness fade; a miss leaves the frame; forward materials keep their environment specular (the `SCREEN_SPACE_REFLECTIONS` def never reached them). The deferred mode is unchanged | not filed (an option for forward renderers whose material cannot afford a second evaluation; to discuss) |
| Idempotent `add_visibility_class` | fix | bevy_camera | The hook runs again when a component is removed and reinserted, and each run pushed the class again, so `check_visibility` listed the entity once per repeat. Repeated light probes filled the eight per-view slots and pushed the others out. The hook now adds a class only once | not filed |
